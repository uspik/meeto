# Meeto — Telegram-бот + Mini App для организации мероприятий

Техническая спецификация, v1.0 · 09.08.2026

---

## 1. Обзор

**Meeto** — Telegram Mini App с ботом-компаньоном для создания мероприятий, сбора участников
и координации групп. Бот отвечает за аутентификацию, доставку уведомлений и deep-link'и;
вся содержательная работа (календарь, создание мероприятий, чат, настройки) — в Mini App.

### Ключевые сценарии

1. Пользователь создаёт группу «Волейбол по средам», приглашает 20 человек по ссылке.
2. Создаёт мероприятие: офлайн, зал №3, ср 19:00–21:00, лимит 16 мест, кворум 10 человек
   до вторника 20:00, чек-лист требований («оплатить взнос», «своя форма»).
3. Участники получают пуш в бот, открывают Mini App, жмут «Иду», указывают, что придут
   с 19:30, отмечают выполненные требования.
4. Владельцу приходит уведомление о каждой отметке «оплатил взнос».
5. Во вторник 20:00 планировщик проверяет кворум: набралось 12 → статус `confirmed`,
   всем уходит подтверждение. Не набралось → авто-отмена, всем уходит отмена.
6. В календаре участника мероприятие — зелёный круг с фото зала; если он согласился ещё
   и на день рождения в это же время, зона пересечения подсвечена красным.

## 3. Аутентификация

1. Mini App открывается — SDK отдаёт `initData`.
2. `POST /api/v1/auth/telegram` с заголовком `Authorization: tma <initData>`.
3. Сервер валидирует HMAC-SHA256 подпись секретом бота, проверяет `auth_date`
   (не старше 24 ч), upsert'ит пользователя.
4. Ответ: пара JWT — `access` (15 мин) и `refresh` (30 дней, ротация, хранится в Redis).
5. WebSocket-подключение авторизуется одноразовым тикетом (`POST /ws/ticket`, TTL 30 с) —
   токен не светится в query-строке логов.

Deep-link'и бота: `t.me/MeetoBot/app?startapp=e_<event_id>` — открывает Mini App сразу
на карточке мероприятия; `?startapp=g_<invite_code>` — приглашение в группу.

## 4. Роли и права

### Базовые роли

| Роль | Назначение |
|---|---|
| `owner` | Создатель группы. Один на группу, передаётся явно. |
| `admin` | Полное управление, кроме удаления группы и смены владельца. |
| `moderator` | *(предлагается)* Модерация чата + верификация требований. |
| `organizer` | *(предлагается)* Может создавать мероприятия от имени группы, но не управлять людьми. |
| `member` | Участвует в мероприятиях, пишет в чат. |
| `guest` | *(предлагается)* Только просмотр и RSVP по прямому приглашению; чат — read-only. |

## 5. Модель мероприятия

### Жизненный цикл

```
draft ──publish──► published ──┬── quorum_ok / manual ──► confirmed ──► completed
                               ├── quorum_failed ──────► cancelled
                               └── cancel ─────────────► cancelled
```

- `draft` — черновик, виден только автору.
- `published` — опубликовано, идёт сбор RSVP. Если кворум не задан, событие сразу считается
  состоявшимся (визуально = `confirmed`).
- `confirmed` — кворум достигнут (досрочно или на дедлайне) либо подтверждено вручную.
- `cancelled` — отменено (авто по кворуму или вручную), в календаре оранжевое.
- `completed` — время прошло; можно отметить фактическую явку (`attended` / `no_show`).

### Поля

| Поле | Тип | Комментарий |
|---|---|---|
| `title` | text | обязательное |
| `description` | text | markdown-lite, опционально |
| `format` | enum | `online` / `offline` / `hybrid` |
| `location_text` | text | адрес/название площадки (для offline/hybrid) |
| `location_geo` | geography(Point) | опционально, для карты и «как добраться» |
| `online_url` | text | ссылка на созвон (для online/hybrid), видна только идущим |
| `starts_at`, `ends_at` | timestamptz | `ends_at` опционально (открытый конец) |
| `timezone` | text | IANA-зона места проведения, для корректного отображения |
| `is_time_flexible` | bool | если true — участник указывает своё окно присутствия |
| `cover_url` | text | пользовательское фото для круглой иконки в календаре |
| `cover_color` | text | fallback-цвет, если фото нет |
| `capacity_max` | int? | лимит мест |
| `waitlist_enabled` | bool | лист ожидания при заполнении |
| `quorum_min` | int? | минимум участников для проведения |
| `quorum_deadline` | timestamptz? | до какого момента нужно собрать `quorum_min` |
| `auto_cancel_on_quorum_fail` | bool | по умолчанию true |
| `rsvp_deadline` | timestamptz? | после — ответы закрыты |
| `visibility` | enum | `group` / `invite_only` / `public_link` |
| `allow_plus_ones` | bool + `max_plus_ones` | участник может привести гостей (занимают места) |
| `status` | enum | см. выше |

### Логика лимита мест

Все изменения RSVP выполняются в транзакции с `SELECT ... FROM events WHERE id=? FOR UPDATE`,
чтобы исключить овербукинг при гонке.

```
seats_taken = Σ(1 + plus_ones) по участникам со статусом going
```

- `seats_taken + requested > capacity_max` и `waitlist_enabled` → статус `waitlisted`,
  `waitlist_position = max+1`.
- Участник отказался → освободившиеся места отдаются листу ожидания по FIFO;
  промоутируется первый, кому мест хватает. Уведомление `waitlist.promoted`,
  окно на подтверждение — 6 ч (настраивается), иначе следующий по очереди.
- `capacity_max` нельзя опустить ниже текущего `seats_taken`.

### Логика кворума

Проверка запускается тремя триггерами:

1. **При каждом RSVP** — если `going_count >= quorum_min` и статус `published`
   → досрочный `confirmed` + уведомление `quorum.reached` (владельцу и всем идущим).
2. **За N часов до `quorum_deadline`** (по умолчанию 25% оставшегося времени, минимум 2 ч)
   — если не хватает, уведомление `quorum.at_risk` владельцу и приглашённым без ответа:
   «Не хватает 3 человек, решение в 20:00».
3. **В `quorum_deadline`** — достигнут → `confirmed`; не достигнут и
   `auto_cancel_on_quorum_fail` → `cancelled` + `quorum.failed`; иначе владельцу
   уходит запрос на ручное решение (кнопки «Провести» / «Отменить»).

Если после досрочного подтверждения участники отказались и счётчик упал ниже кворума,
владельцу уходит `quorum.dropped_below`, но авто-отмены не происходит — решение за ним.

### Требования (чек-лист)

`event_requirements` — упорядоченный список пунктов. Каждый пункт:

- `title`, `description`
- `kind`: `checkbox` (просто отметить) · `text` (ввести значение) · `number` ·
  `file` (загрузить фото/документ)
- `is_mandatory` — без выполнения нельзя перейти в `going` (мягкий вариант:
  можно, но с плашкой «есть невыполненные требования»)
- `requires_verification` — отметка участника попадает в статус `pending`, пока
  владелец/модератор не подтвердит
- `notify_on_complete` — **включается для каждого требования отдельно**; при отметке
  владельцу (и подписанным админам) уходит уведомление
  `«Иван отметил: Оплатить взнос — 1500 ₽»`
- `due_at` — опциональный срок выполнения; за 24 ч участнику уходит напоминание

Прогресс участника (`3/5`) виден в карточке мероприятия; владелец видит матрицу
«участники × требования» с фильтром «не выполнили».

### Ответ участника (RSVP)

| Статус | Значение |
|---|---|
| `invited` | приглашён, не ответил → в календаре **серый** |
| `going` | идёт → **зелёный** |
| `maybe` | под вопросом → **серый с пунктирной обводкой**, места не занимает |
| `declined` | отказ → **серый**, по умолчанию скрыт (переключатель «показывать отклонённые») |
| `waitlisted` | лист ожидания → **серый с жёлтой точкой** |
| `attended` / `no_show` | пост-фактум, для статистики |

При `is_time_flexible = true` участник указывает `arrival_at` / `departure_at` в пределах
окна мероприятия. Эти значения используются и для расчёта пересечений, и для показа
владельцу гистограммы «сколько людей в каждый момент времени».

## 6. Календарь

### Режимы

- **Месяц** — сетка 7×6. В ячейке дня до 3 круглых иконок 24 px (обложка мероприятия
  или инициалы на `cover_color`) + «+N». Кольцо вокруг иконки — цвет статуса.
  Красная точка в углу дня = есть конфликт.
- **Неделя / День** — временная шкала, блоки по вертикали, слева круглая иконка.
  Именно здесь рисуется слой пересечений.
- **Список** — лента предстоящих, сгруппированная по дням.

### Цветовая семантика

| Состояние | Цвет | Токен |
|---|---|---|
| Не участвую (`invited`/`declined`/`maybe`) | серый | `--meeto-neutral` `#8E8E93` |
| Принято (`going`) | зелёный | `--meeto-accept` `#34C759` |
| Отменено (`cancelled`) | оранжевый | `--meeto-cancel` `#FF9500` |
| Пересечение двух принятых | красный | `--meeto-conflict` `#FF3B30` |

Отменённое мероприятие сохраняет оранжевый независимо от RSVP и не участвует в расчёте
конфликтов.

### Расчёт пересечений

Берутся только события со статусом RSVP `going` и статусом события ≠ `cancelled`.
Интервал участника: `[arrival_at ?? starts_at, departure_at ?? ends_at ?? starts_at + 1h)`.

Алгоритм — sweep line по отсортированным началам, O(n log n). Результат —
список отрезков `{from, to, event_ids[]}`. Отрисовка: поверх блоков мероприятий кладётся
абсолютно позиционированный слой с красной заливкой (`rgba(255,59,48,.35)`) и красной
рамкой на пересекающихся блоках. В режиме «месяц» конфликт схлопывается в красную точку.

Сервер отдаёт конфликты уже посчитанными (`GET /calendar?...&with_conflicts=true`),
клиент пересчитывает локально при оптимистичном изменении RSVP.

## 7. Уведомления

### Каналы

`bot` (сообщение от бота) · `inapp` (бейдж и лента внутри Mini App) · `off`.
Если пользователь заблокировал бота — флаг `is_bot_blocked`, доставка деградирует в `inapp`.

### Типы событий

**Мероприятия**

`event.invited` · `event.published_in_group` · `event.updated` (изменилось время/место —
отдельный текст с diff) · `event.cancelled` · `event.reminder` (несколько,
lead-time настраиваемый) · `event.starting_now` · `event.completed_feedback`

**Наполняемость**

`rsvp.received` (владельцу: кто-то ответил) · `rsvp.declined_late` (отказ после
`rsvp_deadline`) · `capacity.full` · `waitlist.promoted` · `waitlist.joined`

**Кворум**

`quorum.reached` · `quorum.at_risk` · `quorum.failed` · `quorum.dropped_below` ·
`quorum.decision_required`

**Требования**

`requirement.completed` (владельцу, per-requirement) · `requirement.verified` /
`requirement.rejected` (участнику) · `requirement.overdue` · `requirement.pending_before_event`

**Группа и чат**

`group.invited` · `group.join_request` · `group.role_changed` · `chat.mention` ·
`chat.reply` · `chat.message` (по умолчанию off, только бейдж)

**Дайджесты**

`digest.daily` (утром — что сегодня) · `digest.weekly` (вс вечером — неделя вперёд)

### Модель настроек

Разрешение считается по цепочке с приоритетом «ближе к объекту — важнее»:

```
default (системный) ◄ user global ◄ group override ◄ event override (mute/unmute)
```

Хранится в `notification_prefs (scope, scope_id, user_id, event_type, channel,
lead_times int[], enabled)`.

Дополнительно:

- **Тихие часы** (`quiet_hours_start/end` в таймзоне пользователя) — некритичные
  уведомления откладываются до конца окна; `event.cancelled` и `event.starting_now`
  игнорируют тихие часы.
- **Батчинг** — для мероприятий с >20 участниками `rsvp.received` агрегируется:
  одно сообщение раз в 15 мин («+4 идут, 1 отказался, всего 12/16»).
- **Дедупликация** — `dedup_key` в outbox, уникальный индекс; повторная постановка
  той же задачи не создаёт второе сообщение.

### Доставка

Транзакционный **outbox**: бизнес-операция и запись в `notifications` — в одной
транзакции; воркер разбирает очередь, шлёт через Bot API с учётом лимитов
(30 msg/s глобально, 1 msg/s на чат), экспоненциальный ретрай на `429`/5xx,
5 попыток, затем `failed`. `tg_message_id` сохраняется — сообщения-карточки
мероприятия редактируются при изменении статуса, а не дублируются.

## 8. Чат

Собственный чат в Mini App (по итогам обсуждения — вариант с полным контролем).

- Тред создаётся автоматически: один на группу + один на каждое мероприятие.
- Транспорт: WebSocket, комната `chat:<chat_id>`. Между инстансами — Redis Pub/Sub.
- История: пагинация курсором по `(created_at, id)` в обратном порядке, 50 сообщений.
- Функции: реплаи, упоминания `@username`, реакции, закрепление, редактирование (15 мин),
  soft-delete, вложения (фото/файл через S3, лимит 20 МБ), «печатает…».
- Непрочитанные: `chat_reads.last_read_message_id`, бейдж = `count(id > last_read)`.
- Доступ к чату мероприятия: приглашённые + `going` + `waitlisted`; чат группы — все
  участники с `chat.write`.
- Модерация: удаление сообщений, мьют участника на срок, запрет медиа.
- Пуш в бот только на `@упоминание` и реплай (настраивается); остальное — бейдж.
- На будущее: экспорт треда, поиск по сообщениям (pg_trgm), голосования в чате.

## 9. API (v1)

Базовый префикс `/api/v1`. Все ответы — `{data, meta?}`; ошибки —
`{error: {code, message, details}}`.

### Идемпотентность
Все `POST`, изменяющие состояние, принимают заголовок `Idempotency-Key`
(хранение результата в Redis 24 ч) — защита от двойных тапов в мобильном вебвью.

## 11. Нефункциональные требования

- **Производительность:** p95 API < 200 мс; календарь месяца — один запрос;
  доставка уведомления — < 5 с от триггера.
- **Масштаб (цель MVP):** 50 000 пользователей, 5 000 мероприятий/мес, 200 RPS пик.
- **Надёжность:** воркеры идемпотентны; планировщик кворума устойчив к перезапуску
  (проверка «просроченных» дедлайнов при старте).
- **Приватность:** телефон и контакты не собираются; `online_url` виден только идущим;
  экспорт и удаление данных пользователя по запросу (GDPR-friendly); срок хранения
  сообщений чата настраивается на уровне группы.
- **Безопасность:** валидация `initData` на каждом входе, RLS-подобные проверки
  доступа в сервисном слое, rate limit на RSVP и отправку сообщений, санитизация
  markdown, подписанные URL для S3.
- **Локализация:** ru/en, ключи через i18next; все даты — в таймзоне пользователя
  с подписью зоны мероприятия, если они различаются.
- **Наблюдаемость:** структурные логи с `request_id`, метрики (конверсия
  приглашение→going, доля событий, отменённых по кворуму), Sentry.

## 12. Дорожная карта

**Этап 1 — Ядро (3–4 недели)**
Аутентификация, группы и роли, создание мероприятий, RSVP, календарь (месяц + список)
с цветовыми статусами и круглыми иконками, базовые уведомления (приглашение,
напоминание, отмена).

**Этап 2 — Наполняемость (2 недели)**
Лимит мест + лист ожидания, кворум с дедлайном и авто-отменой, чек-листы требований
с уведомлением владельца, матрица выполнения.

**Этап 3 — Коммуникация (2–3 недели)**
Чат групп и мероприятий по WebSocket, упоминания, вложения, модерация,
полный центр настроек уведомлений, тихие часы, батчинг.

**Этап 4 — Полировка (2 недели)**
Режимы недели/дня с визуальным слоем пересечений, дайджесты, inline-режим,
повторяющиеся мероприятия, аналитика группы, экспорт в .ics.

**Бэклог**
Оплата взносов через Telegram Payments · геолокация и «кто рядом» · публичные
страницы мероприятий · QR-чекин на входе · интеграция с Google Calendar ·
шаблоны мероприятий · опросы для выбора времени (в стиле Doodle).
